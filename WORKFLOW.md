# Как мы доводили устройства до управляемого состояния

Короткое пояснение для незнакомых с Ansible. Объясняет, **почему** мы использовали
сразу несколько разных инструментов (telnet → expect → SSH → Ansible) и **в каком
порядке**.

---

## Главная проблема - курица или яйцо?

Хочется: **Ansible** заходит на устройство по сети и пушит конфиг. Удобно, повторяемо, документировано.

Но: **Ansible работает через SSH**. А свежий роутер из EVE-NG - это пустая болванка
с дефолтным конфигом. На нём:

- ❌ нет IP-адреса в нашей mgmt-сети (`192.168.100.0/24`)
- ❌ нет пользователя `admin`
- ❌ нет SSH-сервера (нет RSA-ключей)

Чтобы Ansible смог зайти, ВСЁ это нужно настроить. А чтобы это настроить - нужно
сначала каким-то способом войти. **Курица - яйцо.**

Решение: цепочка из трёх инструментов, каждый берёт устройство на следующий уровень.

```
свежий роутер  →  [консоль/telnet]  →  устройство с SSH  →  [Ansible]  →  готовый конфиг
                  ручной + expect                          по сети
```

---

## Инструменты - что каждый делает

### 1. Консоль EVE-NG (через PuTTY)

**Самый низкий уровень.** Виртуальный последовательный кабель. Работает всегда,
даже на устройстве с дефолтным конфигом. Не требует никаких сетевых настроек.

В нашей лабе консоль открывается из EVE-NG GUI - клик "Console" на ноде запускает
PuTTY с правильным портом telnet к хосту EVE-NG.

Используется **один раз** на устройство - чтобы залить bootstrap-конфиг
(loopback + mgmt IP + юзер + домен), после которого устройство станет доступно
по сети.

### 2. Telnet (по сети, но без шифрования)

Когда у устройства уже есть mgmt IP - к нему можно ходить по сети. Telnet - самый
простой способ: открытый протокол, никаких ключей, только логин/пароль.

Шифрования нет, но в лаборатории внутри VMware это не проблема.

Использовали **временно**, как мостик. После заливки bootstrap-конфига устройство
слушает telnet (`transport input ssh telnet` в vty), но ещё не slышит SSH - RSA-ключи
не сгенерированы.

### 3. expect - автоматизация telnet'а

`expect` - это утилита-скриптовалка, которая умеет "общаться" с интерактивными
программами. Запускает программу (`spawn telnet ...`), ждёт определённый текст
(`expect "Password:"`) и шлёт ответ (`send "cisco\r"`).

Эквивалент того, как ты сам бы зашёл telnet'ом и набрал команды - только программа
делает это за тебя и сразу на десяти устройствах.

Использовали expect **один раз пачкой** на 14 роутеров - telnet'нулся на каждого,
сгенерировал RSA-ключи, сохранил конфиг. Результат: SSH везде заработал, telnet
больше не нужен.

### 4. SSH (по сети, с шифрованием)

Шифрованный канал. Стандарт индустрии. Все современные инструменты автоматизации
(Ansible, NAPALM, Netmiko и т.д.) работают через SSH.

Чтобы он включился на циске, нужны:
- IP-адрес ✓ (bootstrap)
- Юзер ✓ (bootstrap)
- Домен ✓ (bootstrap)
- **RSA-ключи** ← вот это критично, генерится отдельно командой `crypto key generate rsa`

### 5. Ansible

**Менеджер конфигурации.** Высокий уровень: ты говоришь "хочу чтобы R12 имел такой-то
конфиг", Ansible сам ходит, сравнивает с текущим состоянием и применяет разницу.

Удобства, которых нет у голого telnet/SSH:
- **Инвентори** (`inventory.yml`) - список устройств, группы (по сайту, по типу)
- **Переменные** (`host_vars/R12.yml`) - данные про устройство, отдельно от логики
- **Шаблоны** (`templates/device.j2`) - Jinja, рендерит конфиг из переменных
- **Идемпотентность** - повторный запуск ничего не меняет, если состояние уже правильное
- **`--check --diff`** - показать что будет сделано, не делая
- **`--limit`** - ограничить набор устройств

Конкретный плейбук `playbooks/apply.yml` берёт `templates/device.j2`, подставляет
переменные для каждого хоста и пушит через модуль `cisco.ios.ios_config`.

## Что мы сделали по порядку

### Этап 1. Подготовка плацдарма

- В EVE-NG добавили ноду `Cloud1` - внутренний бридж для mgmt-сети `192.168.100.0/24`.
- На EVE-хосте дали `pnet1` IP `192.168.100.1/24` - теперь EVE-хост видит роутеров.
- На каждом роутере увеличили Ethernet portgroups до 2 - появился `Ethernet1/3`.
- `Ethernet1/3` каждого роутера подключили к `Cloud1`.

### Этап 2. Bootstrap первой партии (SPB, 4 роутера)

Через **PuTTY-консоль** на каждом из R16/R17/R18/R32:
- Вставили базовый конфиг (hostname, loopback, IP на Ethernet1/3, юзер `admin`, домен).
- Команда `crypto key generate rsa modulus 2048` - сгенерировала RSA-ключи (SSH начал слушать).
- `wr` - сохранили.

После этого 4 роутера стали доступны по SSH.

### Этап 3. Поставили Ansible на EVE-хост

- Снесли apt'овский (старый, 2.9, EOL).
- Поставили pip'овский Ansible 6.x (поддерживает Python 3.8 EVE-хоста).
- Поставили `paramiko<3.0` (старые IOL-ключи не работают со свежим paramiko).
- Прогнали тестовый плейбук - Ansible достучался до всех 4 SPB. ✅

### Этап 4. Bootstrap второй партии (остальные 14 роутеров)

Та же процедура через PuTTY (вставили конфиги). НО на этих 14 забыли запустить
`crypto key generate rsa` - пинг идёт, mgmt IP настроен, но **SSH-сервер не слушает**.

Ansible на них не зайдёт. Что делать?

### Этап 5. expect-скрипт догенерил ключи (telnet → telnet)

Так как **telnet на них работает** (bootstrap включил его в `transport input ssh telnet`),
написали `expect`-скрипт, который:

1. Заходит telnet'ом на каждый из 14 роутеров.
2. Логинится `admin`/`cisco`.
3. Заходит в config mode.
4. Запускает `crypto key generate rsa modulus 2048`.
5. Сохраняет (`wr`).
6. Выходит.

После этого **на всех 18 роутерах работает SSH** → Ansible видит всю инфраструктуру.

## Зачем три разных инструмента?

| Когда | Что используем | Почему |
|---|---|---|
| Свежий роутер, нет IP | **Консоль через PuTTY** | Единственный способ войти на пустую железку |
| Bootstrap-config залит, IP есть, но SSH ещё не настроен | **telnet + expect** | telnet работает раньше SSH; expect автоматизирует "повторить на 14 устройствах" |
| SSH работает | **Ansible** | Идемпотентный менеджер конфигурации, declarative-flow |

Каждый инструмент закрывает свою фазу. **Сейчас все 18 роутеров в фазе #3** - Ansible'ом
рулим до конца жизни.

---

## А telnet выключать не надо?

Технически - можно. После того как SSH везде работает, telnet больше не нужен.
В шаблоне `templates/device.j2` есть строка `transport input ssh telnet` - если хочешь
полностью выключить telnet, поменяй на `transport input ssh`, прогоняешь `apply.yml`,
устройства начинают отказывать в telnet'е.

Для лабы я оставил оба - на случай если RSA-ключи на каком-то роутере слетят и
понадобится снова заходить по telnet'у для починки. В проде так не делают.
